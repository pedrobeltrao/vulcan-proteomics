# Retrospective, milestone M2-M6 (outside reviewer)

Scope read: PROMPT.md, RESEARCH_TREE.md, LESSONS.md, all 71 commits, results/*/NOTES.md (grep-level), reviews/. No raw data or large logs. Several claims below are from grep excerpts of NOTES.md files, not full reads.

## 1. What we should stop doing

1. **Shared bench lock as the timing protocol (stop; replace with a reserved resource).** The lock was held >2 h by the xiSEARCH comparator (results/2026-10-27_M5_xl/NOTES.md, M6_quant/NOTES.md), so `scripts/m6/bench.sh` waited 58 min and the M6 per-stage benchmark was abandoned: "the other stages are not locked". Even where locked, every NOTES (E2, M1e, M2b, M5, hw_adapt) reports load average 6-55 from unlocked agents, so the lock does not isolate anything; it only serializes the agents that follow it. Fix: one exclusive slot (`--exclusive` / dedicated allocation) for timing, short holds, and every number carries load average plus a "contended" flag. Also stop quoting speedups (40-65x, 829x) without stating whether the Sage comparator was run under the same load.
2. **Letting agents choose designs on the sets used for claims, then declaring it after the fact.** D7 picked static_gbm_pred by looking at D0/D1 IDs and entrapment over 6 variants (reviews/m3_independent_review.md l.141: "Variant selection did, mildly"). M6d chose its fix on D9 (cae0e98), M6 MBR defaults on D9, and D11 itself notes the peptide-level charge fill was "informed" by D11. Each time the mitigation was a fresh set found afterwards. Rule: before tuning, the agent writes the tuning set and the (different) claim set into its brief; tuning on a claim set is blocked, not just flagged.
3. **Writing post-hoc explanations of gate failures.** D12: the A1 gates (tail-G2, G1, G3) failed, and a plausible cause (human-contaminated S. aureus null, offset nulls shifted human spectra) was found after seeing the failure. The PI handled this correctly, but the underlying problem is that null sets were admitted without a label-blind contamination screen (M3e NOTES, proposal 1), costing a full gate round plus A2 (d8bc6cf, f7a537a) and a fresh null fetch. Define admission rules before fetching any null set (the A2 plan, now in progress, should be standard).
4. **Starting benchmarks that had to be redone (the measurable waste).**
   - M2b: lustre mmap decode 5 s -> 77 s; runs/v1-v3 and `discarded_lustre_mmap/` kept as superseded; GIL-bound two-GPU-thread round reverted.
   - E9: 48/650 downloads (7%) had the right size and wrong SHA-1; 126 outputs quarantined and redone; ~200 deleted RAWs re-downloaded after an OOM (RESEARCH_TREE 3d, E9 NOTES). The data steward had added SHA-1 checks to the fetch script already (d01fbf7, data_verify NOTES) but cohort code trusted size.
   - M5: FASTA `cat` dropped alpha-synuclein (the truth protein) from the first LiP index; re-run.
   - M2c: unreviewed WIP MS1 finder was 650 core-s/run and over-reported features 2.5x.
   - Common cause: the first measurement was taken before a trivial sanity check (checksum, accession present, wrong-analyzer check on D10cf ion trap). Add a 5-minute preflight checklist per dataset/index build.
5. **Duplicated and stale lessons, and duplicated work.** LESSONS.md has 3 pairs of near-identical rules (RAW-on-Lustre x2, reader supervision x2, download checksum x2, FASTA newline x2) and 4 rules about the 4-core node (pin 4 threads, constant 4, 4-core lock) that D5 (13269b3) and `vulcan.hw` (afe8d0e, 19edd7d) made obsolete; the "4 threads" constant lesson contradicts the affinity lesson next to it. Evidence of duplicate effort: M1e produced baselines twice (results/2026-10-26_M1e_baselines and 2026-10-27_M1e_baselines); two sub-agents each lost a summary.md to the harness guard (already in lessons, but repeated). Also two stale "git_sha -> commit containing all code" fixup commits (7fc78f7, 0165732) show results being committed before code.
6. **Large amounts of uncommitted state.** git status at review time: modified bench/t1/evaluate.py, vulcan/cohort.py; untracked vulcan/gates/a2_*.py (6 files), vulcan/rescore/{fast,post,prod,cohort_scoring}.py, vulcan/predict/library.py, scripts/a2, scripts/scoring_speed, tests/a2, config/, and three results dirs (T1driver_dryrun, scoring_speed, M6_quant/logs). That is the most safety-critical code (A2 admission, rescoring) living only in the working tree on a shared node. Commit WIP to a branch at least every few hours; there is no reason for an A2 gate implementation to be unversioned when pre-registration depends on knowing exactly what was run. Related: earlier loss of /tmp state (mokapot env, mzML conversions, baseline caches) on node move (c49a0e7/2b5e2be, 19edd7d); several M4/M5 inputs still reference `/tmp/vulcan_m4/logs`.
7. **Headline numbers in the status summary that are ahead of the gate record.** The top-of-tree summary leads with "+2.8% IDs over Sage-LDA at 1% (+8.5% at 0.1%)" and "40-65x fewer core-seconds" while the same file says FDR claims are blocked (D12) and the natural-proteome entrapment estimate is 1.1-1.2% at alpha=1% (D14). The caveats are present but a reader of the first paragraph gets the wrong impression; the IDs are at a nominal 1% whose calibration is not established. Also the "A2 ... being implemented" state is not in a commit. Rule: any ID gain is written as "at nominal 1% FDR (unverified)" until gates pass; speed numbers state comparator thread count and load. Note also one summary figure ("~20k runs/h page-cached") is a different regime from the 580 runs/h streaming; keep the lower one next to it.
8. **Mixed decisions/status prose that grows without bound.** RESEARCH_TREE.md is 34 KB with decisions D0-D14 inline; D0 ("only 4 cores") and D2 ("4 cores are the binding resource") are superseded by D5 but still read as active. Mark superseded decisions `[-]` and move them below the fold.

## 2. What worked well (keep)

1. **Independent adversarial review before any sealed look.** Three critiques turned DESIGN v0.1 (several tool-years wide) into the v0.2 minimum deliverable (36b6a92, D1); the M3 review (1df812d, D9) found the first gates weak and an unfair Sage-LDA reference, with no leakage. Amendment A1 was dated before re-run and tagged prereg-v0.4.1. Cost: ~1 day. Payoff: no invalid sealed claim has been made (SEALED_LEDGER.md still closed).
2. **Pre-registration and honest negative results.** D12 records the A1 failures "as recorded" instead of re-scoring the existing nulls; D8 and D10 fix estimator definitions before T2/T3 access; M4 declared E8 truth definitions before use (97daf98). Entrapment verdicts, true FDP at nominal (XL 16% true FDP at 1% before D10) and the 54% natural-over-reversed arm C signal were all reported unfavorably when they were.
3. **Exactness tests as gates (G0 label swap bit-identical, K1 = f32 brute force, top-K recall >= 99.8%, tests/ per milestone).** They caught the `ceil` tie bug in E2 and gave the 40-65x claim a correctness basis. Keep "bit-identity before speed".
4. **Measurement-first engineering.** E1 (30x from direct RawFileReader, 579a25b), M2b profiling (persistent workers, torch-free host code, 65 -> 14 core-s fixed cost) and 2c review (650 -> 29 core-s) each removed the expected bottleneck for a few hours of measurement. The hardware pivot was handled well: `vulcan.hw` plus an hwinfo fingerprint in every benchmark (afe8d0e) and "speed counts only within one node and session" (D5).
5. **Result directories with NOTES.md + metrics.json + timings.jsonl, committed with a tree update.** Almost every milestone has results/ + `tree:` commit pairs and a git_sha, which made this retrospective possible in under an hour. Superseded runs were kept and labeled, not deleted.
6. **Verifier before re-download** (data_verify: 2 of 3 "interrupted" files were already complete) and quarantine-and-redo for corrupt outputs (E9).
7. **Held-out confirmation after tuning** (M6d fixes confirmed on held-out D9 runs and a new dev set D11, with the caveat written down) and the predictor-leakage manifest (D4, 2ace1ba) preventing AlphaPeptDeep on FLR sets.
